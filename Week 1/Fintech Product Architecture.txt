Fintech Product Architecture

1. Product Layers

Our FinTech product is organized into four logical layers.

A) Frontend Layer

This is the public-facing layer where merchants and customers interact with the system.

It consists of:

Merchant Dashboard
Checkout UI

These applications are built using JavaScript frameworks such as ReactJS and VueJS.

Their responsibility is to provide a responsive user interface without implementing business logic.

B) Backend for Frontend (BFF)

The BFF acts as an API gateway specifically designed for frontend applications.

It is implemented in Node.js and is responsible for:

Aggregating data from multiple backend services
Reducing multiple API calls into a single response
Returning frontend-friendly responses

The BFF does not contain core business logic.

C) Backend Microservices Layer

This layer contains independently deployable microservices, each responsible for a specific business capability.

Our backend consists of the following services.

        i) Payment Service (Go)

        Responsible for

        Processing payment requests
        Validating transactions
        Interacting with payment gateways or banking systems
        Publishing payment events after successful transactions

        ii) Ledger Service (Java Spring Boot)

        Responsible for maintaining the financial system of record.

        Its responsibilities include

        Recording debit and credit entries
        Maintaining account balances
        Storing immutable financial transactions

        iii) Notification Service (Node.js)

        Responsible for

        Sending email notifications
        SMS
        Push notifications
        Maintaining notification history

        iv) Fraud Detection Service (ML Python)

        Responsible for

        Detecting suspicious transactions
        Risk scoring
        Running machine learning models
        Analysing relationships between users, devices, merchants and payment patterns

D) Data Layer

Each microservice owns its own database, following the Database-per-Service pattern.

This keeps services loosely coupled and allows each service to choose the database technology best suited to its workload.

        i) Ledger Service uses MySQL

        Ledger data requires strong consistency and ACID-compliant transactions because financial records must always remain accurate.

        MySQL is therefore an ideal choice for storing ledger entries and account balances.

        ii) Payment Service uses MySQL + Valkey

        Payment processing requires transactional consistency, making MySQL suitable for storing payment records.

        Valkey is used as an in-memory cache for frequently accessed data such as sessions, temporary payment states, API rate limiting, and idempotency keys, significantly improving response times.

        iii) Notification Service uses MongoDB

        Notification payloads often vary between email, SMS, and push notifications.

        MongoDB's flexible document model allows these varying structures to be stored efficiently without requiring rigid schemas.

        iv) Fraud Service uses Neo4j + Valkey

        Fraud detection depends heavily on analysing relationships between entities such as customers, merchants, devices, IP addresses, and payment cards.

        Neo4j, a graph database, efficiently traverses these complex relationships to detect fraud patterns.

        Valkey is additionally used to cache frequently accessed fraud scores and temporary risk calculations.

        v) OpenSearch

        Application logs generated by all microservices are centralized into OpenSearch, enabling real-time monitoring, troubleshooting, and operational analytics.

        Older logs are being archived to Amazon S3 using lifecycle policies for long-term retention.

2. Event-Driven Architecture (EDA)

Our platform follows an Event-Driven Architecture using Apache Kafka as the messaging backbone.

Kafka enables asynchronous communication between independent microservices while keeping them loosely coupled.

Successful Payment Workflow:
1. A customer initiates payment through the Checkout UI.
2. The request is routed through the BFF.
3. The BFF forwards the request to the Payment Service.
4. The Payment Service validates the request and processes the payment with the external payment gateway or banking system.
5. Once the payment succeeds, the Payment Service stores the transaction in MySQL and publishes a Payment Successful event to Kafka.
6. The Ledger Service consumes the event and records the corresponding debit and credit entries in the ledger.
7. The Fraud Detection Service consumes the same event and evaluates the transaction using machine learning models and graph analysis. If suspicious activity is detected, it generates a fraud alert.
8. The Notification Service also consumes the event and sends confirmation emails, SMS messages, or push notifications to the customer and merchant.
9. Throughout the workflow, each microservice independently writes application logs to OpenSearch. Older logs and backups are archived to Amazon S3 according to lifecycle policies.
